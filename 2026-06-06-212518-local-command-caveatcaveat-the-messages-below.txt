     Split screens into *.screen.tsx + *.container.tsx

     Context

     src/screens/Posts.screen.tsx and src/screens/Details.screen.tsx currently
     mix two concerns:

     1. Screen customization — extracting route params, configuring the
     navigation header (setOptions, headerRight), and triggering navigation.
     2. Feature logic and UI — Zustand store wiring, data loading effects, list
     rendering, swipeable row state, the detail body.

     We want the *.screen.tsx file to hold only what is unique to it being a
     navigator screen, and move everything else into a sibling *.container.tsx.
     This makes the containers easy to read, test, and reuse independently of
     React Navigation.

     Design

     For each screen, two files:

     - Name.screen.tsx — default export consumed by Root.navigator.tsx. Receives
      React Navigation props. Responsibilities only: read route.params, call
     navigation.setOptions / useLayoutEffect, build navigation callbacks, render
      <NameContainer ... />.
     - Name.container.tsx — named export. Navigation-agnostic: takes plain
     domain props (ids, callbacks). Holds all store hooks, effects, memoized
     data, subcomponents, and styles.

     Subcomponents stay colocated (no new components/ folder):
     - PostRow lives in Posts.container.tsx.
     - FavoriteHeaderButton lives in Details.screen.tsx (it is rendered inside
     headerRight, which is a screen-level concern).

     Files to change

     src/screens/Posts.container.tsx (new)

     - Named export PostsContainer.
     - Props: { onPostPress: (id: number) => void }.
     - Moves from Posts.screen.tsx:
       - PostRow / PostRowComponent and the PostRowProps type.
       - All usePostsStore / useFavoritesStore hooks.
       - openSwipeableRef, handleSwipeOpen, closeOpenSwipeable.
       - sections useMemo, useEffect for loadPosts / loadFavorites, renderItem.
       - Loading / error / SectionList rendering.
       - All related styles.
     - The internal handlePostPress is replaced by calling
     props.onPostPress(id).

     src/screens/Posts.screen.tsx (rewrite)

     - Default export PostsScreen({ navigation }: PostsScreenProps).
     - Defines handlePostPress = useCallback(id => 
     navigation.navigate('Details', { postId: id }), [navigation]).
     - Returns <PostsContainer onPostPress={handlePostPress} />.
     - No styles, no store imports.

     src/screens/Details.container.tsx (new)

     - Named export DetailsContainer.
     - Props: { postId: number }.
     - Moves from Details.screen.tsx:
       - usePostsStore(s => s.posts.find(p => p.id === postId)).
       - Not-found view and the ScrollView body.
       - The body / image / title styles (container, image, title, body,
     centered).
     - Does not know about navigation or favorites — FavoriteHeaderButton stays
     in the screen.

     src/screens/Details.screen.tsx (rewrite)

     - Default export DetailsScreen({ route, navigation }: DetailsScreenProps).
     - Keeps FavoriteHeaderButton, renderFavoriteHeaderRight, the
     useLayoutEffect that sets headerRight, and the headerStar / headerStarOn
     styles (header-only concern).
     - Returns <DetailsContainer postId={postId} />.

     src/navigation/Root.navigator.tsx

     - No changes. Continues to import default exports from
     ./screens/Posts.screen and ./screens/Details.screen.

     Conventions followed

     - File naming matches existing *.screen.tsx convention; new *.container.tsx
      mirrors it (per [[feedback_file_naming]]).
     - State architecture is preserved — containers call Zustand stores, which
     call repositories (per [[feedback_state_architecture]]). No component-to-DB
      calls are introduced.
     - No new dependencies, no schema or store changes.

     Context

     code: they read route params, set header options, wire navigation
     callbacks).

     are the feature/UI layer: store wiring, rendering, styles).

     This makes the import paths reflect the intent — navigator code groups with
      screens, feature code groups with containers — and removes the
     now-misleading src/screens/ folder.

     Add cached per-post details fetch

     Context

     Today the app fetches the full list from
     https://jsonplaceholder.typicode.com/posts once and caches it in the local
     posts table; the Details screen reads from the in-memory list. We now want
     the Details screen to also call
     https://jsonplaceholder.typicode.com/posts/{id} and persist that response
     so subsequent opens of the same post never refetch (across navigation and
     across app restarts).

     The details payload is currently the same shape as a list item but may
     diverge in the future. To make that evolution painless, details get their
     own table, repository, and store — posts stays as the "list" cache and is
     untouched.

     Design

     Schema — new post_details table

     src/db/schema.ts:

     export const postDetails = sqliteTable('post_details', {
       postId: integer('post_id').primaryKey().references(() => posts.id),
       userId: integer('user_id').notNull(),
       title: text('title').notNull(),
       body: text('body').notNull(),
       fetchedAt: integer('fetched_at').notNull(),
     });

     export type PostDetails = typeof postDetails.$inferSelect;
     export type NewPostDetails = typeof postDetails.$inferInsert;

     fetchedAt is a timestamp (cheap; leaves room for staleness eviction later).
      The duplicated title/body are intentional — when the details API diverges
     (e.g. adds comments or relatedPosts), we extend this table and posts stays
     as the list cache.

     Migration is generated via npx drizzle-kit generate per
     [[feedback_drizzle_migrations]] (no hand-written CREATE TABLE). The new
     0003_*.sql must be wired into src/db/migrations/migrations.ts next to
     m0000…m0002.

     API — src/api/posts.api.ts

     Add alongside fetchPosts:

     export async function fetchPostById(id: number): Promise<ApiPost> {
       const response = await
     fetch(`https://jsonplaceholder.typicode.com/posts/${id}`);
       if (!response.ok) {
         throw new Error(`Fetch failed: ${response.status}`);
       }
       return response.json() as Promise<ApiPost>;
     }

     Reuses the existing ApiPost type and the same error pattern as fetchPosts.

     Repository — src/repositories/post-details.repository.ts (new)

     import { eq } from 'drizzle-orm';
     import { db } from '@db/index';
     import { postDetails } from '@db/schema';
     import type { NewPostDetails } from '@db/schema';

     export const postDetailsRepository = {
       getById: (postId: number) => db.select()
         .from(postDetails)
         .where(eq(postDetails.postId, postId))
         .get(),
       upsert: (row: NewPostDetails) => db.insert(postDetails)
         .values(row)
         .onConflictDoUpdate({ target: postDetails.postId, set: row })
         .run(),
     };

     Same shape as postsRepository and favoritesRepository.

     Store — src/stores/post-details.store.ts (new)

     Mirrors usePostsStore / useFavoritesStore per
     [[feedback_state_architecture]] — components never touch the DB directly.

     State:

     type PostDetailsState = {
       detailsById: Record<number, PostDetails>;
       loadingIds: Set<number>;
       errorById: Record<number, string>;
       loadPostDetails: (id: number) => Promise<void>;
     };

     loadPostDetails(id):
     1. If detailsById[id] already in memory → return.
     2. Else read from postDetailsRepository.getById(id); if found, hydrate
     detailsById[id] and return (no network).
     3. Else mark loadingIds with id, call fetchPostById(id), upsert into the
     repo with fetchedAt: Date.now(), set detailsById[id], clear loading.
     4. On error, set errorById[id] and clear loading.

     This satisfies "cache the result and don't request again on future opens"
     across both same-session and across-restart cases.

     UI — src/containers/Details.container.tsx

     Currently reads the post from usePostsStore. Change to:

     - Read imageUrl from the in-memory list (usePostsStore.posts.find(...)) —
     the API has no image, so the list cache stays the source of truth for that.
     - Read details (title, body, userId) from
     usePostDetailsStore.detailsById[postId].
     - Read usePostDetailsStore.loadingIds.has(postId) and errorById[postId].
     - useEffect: call loadPostDetails(postId) on mount.
     - Render rules:
       - If errorById[postId] → error text (mirrors the Posts container error
     view).
       - Else if no cached details and loading → <ActivityIndicator size="large"
      /> centered (matches Posts loading style).
       - Else render the ScrollView body with image + title + body.

     The "Post not found" branch (when the list doesn't contain the id) stays as
      a guard for deep-link / inconsistent-state edge cases.

     Persist-cache post thumbnails with @d11/react-native-fast-image

     Context

     Post-list thumbnails (25×25 picsum URLs stored per row in SQLite) currently
      render through React Native's built-in <Image>, which leans on NSURLCache
     (iOS) / OkHttp cache (Android). Those caches honor picsum's Cache-Control
     headers but offer no LRU guarantees and can silently evict, causing visible
      re-downloads when scrolling or relaunching. We want the thumbnails (and
     the Details image) to come from a real persistent disk cache so the same
     URL never hits the network twice in practice.

     @d11/react-native-fast-image is the maintained fork of
     react-native-fast-image and wraps SDWebImage (iOS) + Glide (Android), both
     of which ship with disk-backed LRU caches managed natively. It works with
     the New Architecture (which this project has enabled — see CLAUDE.md). The
     two <Image source={{ uri }} /> call sites swap to <FastImage source={{ uri 
     }} />.

     Design

     Install

     - npm install @d11/react-native-fast-image
     - bundle exec pod install from ios/ (per CLAUDE.md: CocoaPods manages all
     iOS deps).
     - No Android Gradle step is required (autolinking).

     Wrap with a thin internal component — src/components/CachedImage.tsx (new)

     A tiny adapter so the rest of the codebase doesn't import the vendor name
     directly. Future migrations (e.g. to expo-image) only touch this one file.

     import FastImage, { type FastImageProps } from
     '@d11/react-native-fast-image';

     export type CachedImageProps = FastImageProps;

     export function CachedImage(props: CachedImageProps) {
       return <FastImage {...props} />;
     }

     (One file, one re-export — does not add abstraction beyond what's needed,
     per the project's no-premature-abstraction rule.)

     import { faker } from '@faker-js/faker';
